# Real Data Failure Modes

"O que pode dar errado quando dado real de cliente entra neste codebase?" — lista de riscos
concretos, cada um com detecção, impacto, prevenção e recuperação. Não é teórico: cada item
abaixo mapeia a uma limitação já conhecida do código atual (`docs/context/TECH_DEBT.md`,
`docs/domain/AGRO_INGESTION_CONTRACT.md`) ou a um invariante que só foi testado contra dado
sintético.

| Failure | Detection | Impact | Prevention | Recovery |
|---|---|---|---|---|
| **Extractor emite zero objeções silenciosamente — `role="lead"` nunca resolvido** | Confirmado por auditoria de código nesta sessão: o parser Agro tem resolução de `closer` (`_resolve_closer`) mas nenhuma resolução equivalente de `lead` — participantes ficam `role="unknown"` a menos que a fonte já traga `role="lead"` explícito (hipótese não confirmada). `RuleBasedObjectionExtractor` só escaneia `role="lead"`. Sem detecção automática hoje — um `Call` válido com zero objeções é indistinguível de "esta call realmente não teve objeção" | **Alto — o mais crítico desta lista.** Roda contra dado real, produz `Call` válido, mas o extractor não detecta nada em nenhuma call, sem nenhum erro/flag visível | `docs/data/FIRST_CALLS_VALIDATION.md` passo 13 (novo, adicionado nesta rodada) exige confirmar resolução de `role="lead"` ponta a ponta antes de qualquer avaliação do extractor contra dado real | Não há correção de dado — é gap estrutural do parser/adapter (fora do escopo desta task alterar); reportar como blocker de engenharia antes de qualquer avaliação do extractor v0 contra dado real |
| Participante não resolvido (`unresolved_speaker`) vira `role="unknown"` e é ignorado pelo extractor | Nenhuma detecção automática hoje — é uma variante silenciosa do item acima: mesmo com resolução de `lead` funcionando para a maioria, um speaker específico não resolvido ainda cai fora do escopo do extractor sem aviso | Médio a alto — perde objeções reais ditas por um participante específico, sem sinal de que isso aconteceu | Revisar taxa de `unresolved_speaker` no relatório de qualidade (`docs/data/DATA_QUALITY_REPORT.md`) como proxy indireto — não é detecção direta | Reprocessar depois de melhorar a resolução de speaker na fonte/parser |
| Timestamps de segmento interpretados como absolutos quando são relativos (ou vice-versa) | `docs/data/SOURCE_CONTRACT_DIFF_TEMPLATE.md` já lista este campo como não confirmado; `docs/data/FIRST_CALLS_VALIDATION.md` passo 14 pergunta isso explicitamente | Médio — quebra ordenação de segmentos, cálculo de duração, e qualquer análise de timing dentro da call | Confirmar explicitamente no protocolo de 5 calls antes de qualquer batch | Reprocessar com a interpretação correta — `segment_id` é determinístico por índice, não pelo timestamp em si, então reprocessar não duplica |
| Commit acidental de dado bruto no Git | `git status`/`git diff --check` antes de qualquer commit; `.gitignore` já cobre `data/raw/`, `data/interim/`, `data/processed/private/` | Alto — PII pública, irreversível numa branch já pushada | Nunca `git add -A`; revisar staged files antes de commitar (regra já em vigor nesta sessão); `.gitignore` como rede de segurança, não a única linha de defesa | Se aconteceu: remover do histórico (não só do HEAD), considerar o dado como vazado e avisar o parceiro — decisão humana, não técnica |
| Unidade errada de `duration_seconds` (minutos interpretados como segundos) | `docs/data/SOURCE_CONTRACT_DIFF_TEMPLATE.md` no passo de validação; comparar duração calculada com duração conhecida de 1-2 calls manualmente | Médio — toda métrica de duração fica 60x distorcida, `duration_mismatch` pode disparar em massa | Confirmar unidade explicitamente no protocolo de 5 calls antes de qualquer batch (`docs/data/FIRST_CALLS_VALIDATION.md`, passo 8) | Reprocessar o batch — `call_id`/`segment_id` são determinísticos, reprocessar não duplica |
| Timezone incorreto/ausente em `occurred_at` | `Call`/`Deal`/`StageEvent` já rejeitam datetime naive (`ValueError`) — falha explícita, não silenciosa | Baixo a médio — se a fonte manda um horário local sem tz e o parser assume UTC por engano, a data fica certa mas a hora errada | Confirmar timezone da fonte no protocolo de 5 calls (passo 7); nunca assumir UTC sem confirmar | Reprocessar com o offset correto |
| Colisão de nome funde dois participantes distintos | `participant_id_collision` já é uma flag existente (`docs/domain/AGRO_INGESTION_CONTRACT.md`), mas hoje só sinaliza, não resolve | Médio — atribuição de fala errada entre duas pessoas reais | TD-01/TD-02 (`docs/context/TECH_DEBT.md`) — sem id estável da fonte, o risco é estrutural; monitorar taxa da flag no relatório de qualidade | Não há correção retroativa automática sem um id estável real; revisar manualmente casos flagados antes de confiar na atribuição |
| Atribuição de speaker errada (closer marcado como lead, ou vice-versa) | Revisão manual das 5 primeiras calls (`FIRST_CALLS_VALIDATION.md`, passo 12); grounding metric do eval (`evals/objection_v0`) já detecta objeção atribuída a quem não é lead | Alto para `RuleBasedObjectionExtractor` — ele só olha segmentos de `role="lead"`; se a role estiver invertida, objeções reais são perdidas silenciosamente | Confirmar resolução de `closer` manualmente nas 5 primeiras calls antes do batch | Reprocessar depois de corrigir o mapeamento de role na fonte/parser |
Call duplicada por **reprocessar o mesmo dado duas vezes** | `derive_call_id()` é determinístico — mesmo `(company_id, source, source_id)` sempre produz o mesmo `call_id`; reprocessar o mesmo export não cria uma segunda `Call` | Baixo — mitigado estruturalmente para este caso específico | Confiar no design existente para reprocessamento idempotente | N/A para este caso |
| Call duplicada por **`meeting_id` reusado entre reuniões diferentes** (ex.: sala pessoal/recorrente do Zoom reusa o mesmo número entre ocorrências distintas) | Não detectado automaticamente hoje — duas calls genuinamente diferentes colidiriam no mesmo `call_id` e uma sobrescreveria a outra silenciosamente, o oposto de "duplicada" | Médio a alto, se a fonte real reusar ids de reunião — perda silenciosa de uma das duas calls | Confirmar no protocolo de 5 calls (`docs/data/FIRST_CALLS_VALIDATION.md`, passo 6) se `meeting_id` é único por ocorrência ou reusável (ex.: Zoom tem um id numérico reusável e um `uuid` por ocorrência — confirmar qual a fonte real envia) | Se confirmado reusável, `source_id` precisa incluir um componente adicional que distinga ocorrências (ex.: data/hora) antes de qualquer batch — decisão de mapeamento, não corrigível depois sem reprocessar |
| Deal duplicado (mesmo deal processado duas vezes) | `derive_deal_id()` idem — determinístico por `(company_id, source, external_id)` | Baixo — já mitigado estruturalmente | Idem | N/A |
| OPEN interpretado como LOST (ou qualquer troca de outcome) | `Deal.outcome` não tem default — todo caller deve declarar explicitamente (`src/closer_ai/domain/deal.py`); mas a fonte real de verdade é a semântica do Kommo, ainda não confirmada | Alto — inverte a conclusão de Outcome Intelligence | `docs/data/KOMMO_DISCOVERY.md` — confirmar semântica de status/stage com o negócio antes de mapear, nunca assumir pelo nome do campo | Reprocessar depois de corrigir o mapeamento; nenhuma análise deve rodar sobre outcome não confirmado |
| Mesma Call casada com múltiplos Deals simultaneamente | Não impedido estruturalmente hoje — TD-09 (`docs/context/TECH_DEBT.md`), depende de constraint de storage que não existe | Médio — sem storage layer, o risco é teórico até haver persistência real | Documentar como gate explícito em "MATCHING READY" (`docs/context/EXECUTION_GATES.md`); revisar manualmente antes de qualquer decisão automatizada baseada em match | Reconciliar manualmente os `CallDealMatch` conflitantes |
| PII em logs | `parse_agro_call()` já tem convenção de erro seguro (mensagens citam só `meeting_id`, nunca `str(exc)` do pydantic) — mas essa disciplina precisa se estender a qualquer código novo (Kommo adapter, matching heurístico) | Alto — PII em log pode persistir em sistema de observability fora do nosso controle | Regra de revisão de código: nenhuma exceção/log deve incluir conteúdo de transcript, nome, email, telefone — só ids | Rotacionar/purgar logs afetados; decisão de quem tem acesso ao sistema de log é humana |
| Transcript aparece dentro de uma exceção | Mesma disciplina acima — revisar toda mensagem de exceção nova antes de merge | Alto — mesmo risco de PII em log | Regra de review explícita (já parcialmente aplicada em `AgroParseError`, ver docstring do módulo) | Idem |
| Dataset misturado entre empresas parceiras (Agro e Empreende) | `company_id` já é o campo de tenant em todo o schema (`Call`, `Lead`, `Deal`) — misturar exigiria um erro de configuração explícito no momento da ingestão | Alto — vazamento cruzado entre clientes do AI Closer | Nunca hardcodar `company_id` errado; confirmar o valor correto por fonte antes de qualquer processamento | Reprocessar com o `company_id` correto; auditar se algum resultado já foi exposto com o valor errado |
| IDs de origem instáveis (meeting_id/external_id muda entre re-exports do mesmo dado) | Comparar `checksum`/`record_count` do manifest (`data/manifests/TEMPLATE.yaml`) entre lotes recebidos | Médio — quebra a idempotência que os IDs determinísticos dependem | Confirmar com o parceiro se o id é estável entre exports, não só dentro de um export | Se instável, `derive_call_id`/`derive_deal_id` vão gerar ids diferentes para o "mesmo" registro — decisão de produto sobre como reconciliar, não solução automática |
| Formato de export muda sem aviso (fonte real evolui) | `docs/data/SOURCE_CONTRACT_DIFF_TEMPLATE.md` deve ser reexecutado a cada novo lote significativo, não só na primeira amostra | Médio — parser pode começar a falhar silenciosamente ou gerar `quality_flags` em massa | Monitorar distribuição de `quality_flags` a cada lote (`docs/data/DATA_QUALITY_REPORT.md`) como sinal de drift | Reexecutar o diff de contrato, ajustar o parser conforme necessário |
| Semântica de stage do CRM mal entendida | `docs/data/KOMMO_DISCOVERY.md` separa API shape de business semantics de propósito | Alto — todo o funil de `StageEvent`/Outcome Intelligence fica incorreto | Nunca mapear stage só pelo nome do campo da API — confirmar com quem opera o CRM | Remapear depois de confirmação; reprocessar `StageEvent`s afetados (idempotente pelos IDs determinísticos) |

## Notas

- Vários itens acima ("Call duplicada", "Deal duplicado") já estão estruturalmente mitigados
  pelo design de IDs determinísticos existente — listados aqui para deixar explícito que
  **foram considerados**, não porque sejam risco real hoje.
- Os itens de maior risco real não mitigado (`participant_id_collision`, semântica de stage,
  atribuição de speaker) já têm um item correspondente em `docs/context/TECH_DEBT.md` ou um
  gate correspondente em `docs/context/EXECUTION_GATES.md` — este documento não inventa
  proteção nova, só consolida o risco num único lugar para revisão antes do primeiro batch
  real.
